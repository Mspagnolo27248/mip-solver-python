01What the application is

A planner at a lubricants refinery decides, for every day of the next several weeks, how many barrels of each feed to charge to each process unit. Those charges produce material, customers draw it down, and every product has a tank that can overflow or run dry. The workbook this replaces did that arithmetic in Excel; the application does it in a deterministic engine and then lets a solver search for a better schedule.

Two sides sit on the same facts, and the UI keeps them apart on purpose. The planning side is the workbook: type a charge rate, see the projection move. The optimizer side needs inputs a person working by hand never touches — lost-sale margin, netbacks, switch costs, solver settings — so it gets its own mode rather than putting prices in front of someone who only wants to move a charge.

Three artefacts carry the state a user cares about, and every screen is a view onto one of them: the feeds (what the world says is true today), a Current Plan (a frozen copy of the feeds plus a charge schedule), and an Optimized Result (a Current Plan the solver rewrote). An Optimized Result is itself a scenario, so it opens on the planning side exactly like one a person made.

03The data pipeline

This is the spine. Data moves through four stages, each of which exists to answer one question a planner will eventually ask: what did the source say, what did I change, what was true when I made this plan, and what does that imply?

What feeds a scenario, and from where

Six feeds, three upload slots. Uploads are per-slot, not all-or-nothing: dropping in an open-orders extract leaves inventory and the forecast reading from the workbook seed until their own files arrive.

Reference data — products, tank capacities, yields, maximum rates, control limits — travels separately. It is one versioned JSON document (reference_version.payload) because it changes rarely and always moves as a set. Planner edits to it land in reference_override and bump overrides_version, which is part of the simulation cache key, so editing a yield invalidates every projection built on it.

05The plant being planned

A BA reading the codebase will meet product codes before product names. This is the vocabulary: crude splits into side streams, five process units convert them, and only four of those units are decisions the optimizer gets to make.

Two consequences show up everywhere in the code. First, because those three units run one feed at a time, writing a rate onto one of their charge lines has to clear the siblings on the same days — otherwise the unit is silently scheduled at double rate. Second, because the platformer, the hydrotreater and the transfer lines legitimately carry several lines on one day, the same clearing rule applied there would wipe correct schedules, so it is deliberately not applied.

06The daily balance

Every number the application shows — every alert, every chart, every optimizer objective — comes out of this one cascade, run once per product per day. It is the workbook’s core algorithm and the single most important business rule in the system.

The planning views run the engine in workbook mode, which reproduces Excel exactly — including its first-match VLOOKUP semantics, where a product charged at two units only counts the first line. Simulation.lookup_conflicts lists every product where that differs from summing all matching lines. The optimizer and its referee run in physical mode, with the clamps above, because a schedule has to be scored against what the plant can actually do.

Time convention

Rows fed by the feeds — Production In, Sales, Blends, Forecast — are suppressed on days before the plan’s as_of date. Schedule-driven rows are not. That asymmetry is the workbook’s and is preserved deliberately; it is the reason a plan dated in the past reads as seven weeks of production against no demand.

07Business rules

The rules below are the ones that surprise people. Each is enforced in code, and most exist because the alternative failed quietly once.

  • R1

    An override outranks the source, and survives every sync

    Effective value is override_value if present, else source_value. Syncing a feed moves only the source. If the source moved after the planner typed their override, the cell is flagged stale — shown, not resolved.

  • R2

    A plan freezes its inputs, and its date cannot be corrected

    Creating a Current Plan copies staging into scenario.inputs. There is no endpoint to change a scenario’s as_of afterwards. A plan created with the wrong date has to be made again; nothing downstream detects the error.

  • R3

    A new plan takes fresh data but an inherited schedule

    Opening inventory and demand come from the current feeds; the charge grid and downtime are copied from whichever plan the form names, lined up by calendar date. Days at either end that fall outside the source plan start blank, and the form says how many.

  • R4

    Demand is served before unit charge

    In physical mode the tank covers customer orders first. Unmet demand is a Lost Sale; a unit left without feed is a Feed Shortfall. The optimizer prices those two very differently, so the ordering decides the answer.

  • R5

    Filling a whole unit at a rate is refused; clearing one is not

    Most units carry several charge lines. Writing one rate onto all of them runs every line at once, which no plant can execute. Clearing a whole unit is the operation a cold start needs, and is the one allowed.

  • R6

    On one-feed units, a fill clears the siblings

    MEK, EXTRACT and ROSE run one feed at a time, so setting a rate on one line clears that unit’s other lines on those days. The platformer, the hydrotreater and the transfers carry several lines per day as a matter of course, so theirs are left alone.

  • R7

    Days a unit is down are skipped, never written

    The optimizer creates no variable on an outage day, so a charge typed there would survive into results unnoticed. Fills skip those days upstream, and the referee checks for them downstream.

  • R8

    One optimizer run at a time, and not without its prices

    A second run while one is solving is refused with a 409 naming the plan the busy run is working on. A run is refused with a 400 if lost-sale margin or either netback is unset — the objective is meaningless without them.

  • R9

    Both sides of a comparison are scored over the same days

    A model clamps its horizon back to the last day the planner filled in a charge. Scoring the baseline over the days asked for while scoring the result over the days actually planned flatters the optimizer by exactly the demand in the gap — which it did, by 24 percentage points, before this was fixed.

  • R10

    Every accepted solve is replayed through the simulator

    The optimizer’s KPIs come from its own variables, so they are exactly what not to trust. verify.py re-simulates the proposed schedule as an independent implementation of the same physics. Disagreement marks the run unverified, and an unverified run should not be used.

  • R11

    done is a proof, not a compliment

    done means the solver proved optimality. not_proved_optimal is the normal good outcome on a long horizon, and the only outcome greedy can ever reach — it does no search, so there is no gap to report.

  • R12

    Deleting a plan takes its results with it

    Deleting a Current Plan deletes every Optimized Result made from it and their run cards. Deleting one result leaves results refined from it in place. Both confirm first and name what goes; neither can be undone.

08UI flow

One page, two modes, nine tabs. The scenario picker in the header is global — every view reads whichever plan is selected — and the mode switch decides which tabs exist rather than which are enabled.

Interaction details worth knowing before touching the front end

  • Edits save on blur, not on a button. A charge cell, an override, a reference value and an optimizer input all write when the field loses focus, and the projection re-simulates immediately.
  • The scroll wheel is blurred out of number inputs. A focused number input takes wheel events as increments; scrolling the page past a cell you just typed in once turned 0.30 into −36.7 and ruined a run with nothing on screen to show it.
  • Filled-but-unapplied panels are reported. The downtime and fill panels write nothing until Add or Apply. Leaving one dirty — by closing it, changing tab, or changing plan — raises a toast with a way back to it.
  • Runs are polled, not pushed. The solve is synchronous on the server; the front end tracks it with a clock and a poll, and a run left running by a stopped server reads as interrupted.
Before changing this UI

Run the ui-ux-audit skill over any change to web/index.html, app.js or styles.css before calling it done. It checks the four conventions this screen keeps breaking: one concept keeps one name, one job uses one control, a planner can tell what an action will touch, and nothing fails silently.

09Optimizer run lifecycle

A run is a state machine with a referee in the middle. The important thing to read off it: producing a schedule and being allowed to trust one are two different events.

ModelDecidesTypical time, 42 daysUse it when
greedyMEK, EXTRACT, HYDRO, ROSEunder a secondFirst pass from a cold plan. No optimality gap, ever.
v2MEK, EXTRACT, HYDRO (two-stage)about a minuteRefining a verified greedy result.
v1MEK, EXTRACTvariesSmaller problem; the hydrotreater stays as scheduled.
v0baseline formulationvariesReference implementation and regression target.

The working sequence is greedy then Refine with v2 from the run card: a schedule in seconds, then a solver improving one that already verifies. On the 2026-09-12 walkthrough that took a plan from 8,863,918 gal of lost sales to 947,712 in 2.5 seconds.

11Where the detail goes next

This guide is the map. Five things sit under it that a developer or BA will need within their first fortnight, and none of them exist yet in this form:

  1. An API contract per endpoint — request and response schemas with a worked example each. FastAPI already publishes /docs; what is missing is the meaning of the fields, not their types.
  2. A field-level data dictionary — every column of the twelve tables with its unit, its nullability, who writes it, and what a null means. The units are the trap: gallons, barrels, barrels per day and gallons per day all appear as bare floats.
  3. A business-rules catalogue keyed to code — the twelve rules above expanded to every enforced rule, each with the function that enforces it and the test that pins it. That is the document a BA can actually take to operations.
  4. Screen-by-screen UI specs — per view: what it reads, what it writes, every control, every error state. The ui-ux-audit skill already encodes the conventions these would be written against.
  5. A runbook — first-time setup, the monthly cycle from three uploaded files to a verified plan, and what to do when a run comes back unverified, infeasible or interrupted.

The deep domain material already exists in the repository and should be linked rather than rewritten: BUSINESS-LOGIC.md for the workbook decomposition, PROCESS-FLOW.md for the confirmed plant description, MIP-FORMULATION.md and SCHEDULING-MODEL.md for the optimization model, and MARGIN-AND-CAMPAIGNS.md for how the objective was calibrated.
